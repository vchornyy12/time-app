#### CR-COMP-04-001 — Potential Runtime Panic in `createGCalEvent`
**Rule**: COMP-04 (Type correctness / runtime safety)
**File**: `lib/google/calendar.ts` — Line 51
**fix_capability**: suggested_fix

**Description**: The `createGCalEvent` function uses a non-null assertion `input.scheduledAt!` inside the `else` branch. If a caller passes `allDay: false` (or omits `allDay`) but also omits `scheduledAt`, the expression `new Date(undefined!)` will produce `Invalid Date`, which silently produces `NaN` timestamps that the Google Calendar API will reject with a 400, or in strict TypeScript contexts throw at runtime. The `CalendarEventInput` type marks `scheduledAt` as optional (`scheduledAt?: string`), making this a real path.

**Evidence**: `lib/google/calendar.ts:51` — `const start = new Date(input.scheduledAt!)`

**Suggested Fix**: Add a guard before use:
```typescript
if (!input.scheduledAt) {
  throw new Error('scheduledAt is required for timed calendar events')
}
const start = new Date(input.scheduledAt)
```
Alternatively, model the type as a discriminated union: `{ allDay: true; date: string } | { allDay?: false; scheduledAt: string }`.

#### CR-QUAL-03-001 — `completeProject` silently swallows DB errors
**Rule**: QUAL-03 (Error handling completeness)
**File**: `lib/actions/projects.ts` — Lines 232–243
**fix_capability**: auto_fixable

**Description**: The `completeProject` server action calls `supabase.from('projects').update(...)` but never checks the returned `error` object. If the Supabase update fails (network error, RLS violation, constraint failure), the error is silently discarded and the action returns `undefined` without notifying the caller, leaving the user with no feedback and the project still in `active` status.

**Evidence**:
```typescript
// lib/actions/projects.ts:236–241
await supabase
  .from('projects')
  .update({ status: 'completed' })
  .eq('id', pId)
  .eq('user_id', user.id)
// ← no error check
revalidatePath('/projects')
```

**Suggested Fix**: Destructure and check the error:
```typescript
const { error } = await supabase
  .from('projects')
  .update({ status: 'completed' })
  .eq('id', pId)
  .eq('user_id', user.id)

if (error) throw new Error(error.message)
revalidatePath('/projects')
```

#### CR-APPR-02-001 — `TaskDetailPanel` fetches data client-side, bypassing Server Actions pattern
**Rule**: APPR-02 (Architectural consistency)
**File**: `components/tasks/TaskDetailPanel.tsx` — Lines 78–105
**fix_capability**: manual_required

**Description**: `TaskDetailPanel` directly calls `createClient()` (browser Supabase client) to `select('*')` from `tasks` and `projects` without a user_id filter in the query itself (relying solely on RLS). Every other data-fetching path in this application uses Server Components + Server Actions. This creates an inconsistent pattern, bypasses the type-safe server action boundary, and means this component cannot be server-rendered or statically analyzed for data access.

Additionally, the component fetches `select('*')` which returns all columns including potentially sensitive future fields. It then uses a `mounted` flag pattern that is a class-component era workaround; React 19's `use()` hook or Server Components would be more idiomatic.

**Evidence**: `TaskDetailPanel.tsx:85–99` — direct Supabase `select('*').eq('id', taskId).single()` in a `useEffect`.

**Suggested Fix**: Convert to a `TaskDetailOverlay` that receives the task data as a prop from its parent (which already has the task in scope), or fetch via a Server Action. At minimum, add `.eq('user_id', user.id)` to the project query on line 94–97.

#### CR-NF-REQ-02-001 — `getLogbookDays` overfetches: no server-side pagination of tasks
**Rule**: NF-REQ-02 (Performance / scalability)
**File**: `lib/actions/logbook.ts` — Lines 33–39
**fix_capability**: suggested_fix

**Description**: The logbook action fetches up to `limit * 30` tasks (`30 * 30 = 900` by default) from the database in a single query to derive the `limit` (30) most recent *days*. For active users with many completed tasks, this could fetch thousands of rows to return 30 days of data. The overfetch factor grows unboundedly as `limit` increases.

**Evidence**: `lib/actions/logbook.ts:38` — `.limit(limit * 30)`

**Suggested Fix**: Either use a DB-side `GROUP BY DATE` query, or add a date-range filter based on a rough estimate (e.g., fetch tasks completed within the last `limit * 7` days), then expand the window if not enough distinct days are found. A cursor-based pagination approach using `beforeTimestamp` is already partially implemented but the inner limit multiplier remains.

#### CR-IMPACT-SFX-01-001 — `TaskDetailPanel` client-side project query missing `user_id` filter
**Rule**: IMPACT-SFX-01 (Security side effect)
**File**: `components/tasks/TaskDetailPanel.tsx` — Lines 93–99
**fix_capability**: auto_fixable

**Description**: The project title fetch at line 94 queries `projects` by `id` only, without an explicit `.eq('user_id', user.id)` filter. While RLS should enforce this at the DB level, the explicit filter is a defense-in-depth best practice and is consistent with all Server Action patterns in this codebase. If RLS is ever misconfigured or disabled in a dev environment, this query could return another user's project title.

**Evidence**:
```typescript
// TaskDetailPanel.tsx:94–98
const { data: project } = await supabase
  .from('projects')
  .select('title')
  .eq('id', data.project_id)
  // ← missing .eq('user_id', user.id)
  .single()
```

**Suggested Fix**: Add `.eq('user_id', user.id)` to the project query. The `userId` is already fetched on line 82 of the same component.

#### CR-CONV-01-001 — Hardcoded Tailwind opacity values not in project design token set
**Rule**: CONV-01 (Design token / style consistency)
**File**: `components/clarity/ClarityWizard.tsx` — Lines 36–42
**fix_capability**: manual_required

#### CR-IMPACT-PAT-02-001 — `handlePaste` global listener registered in two components
**Rule**: IMPACT-PAT-02 (Pattern duplication with coupling risk)
**Files**: `components/tasks/AttachmentSection.tsx` (line 181), `components/layout/QuickCaptureBar.tsx` (line 95)
**fix_capability**: suggested_fix

**Description**: Both `AttachmentSection` and `QuickCaptureBar` register a `document.addEventListener('paste', ...)` global listener for screenshot capture. When both components are mounted simultaneously (e.g., a task detail panel is open while the quick capture bar is rendered), both paste handlers fire for the same paste event. `QuickCaptureBar` guards against this with a `barRef.current?.contains(document.activeElement)` check, but `AttachmentSection` registers unconditionally. This can cause a screenshot paste to go to both the task's attachment section AND the capture bar if both are mounted.

**Suggested Fix**: Either extract paste handling into a shared hook (`usePasteUpload`), or add the same `contains(document.activeElement)` guard to `AttachmentSection`'s paste handler.

#### CR-INFO-001 — `deleteAccount` iterates tables with user-scoped client (belt-and-suspenders pattern)
**File**: `lib/actions/account.ts` — Lines 26–40
**Description**: The `deleteAccount` action iterates all user tables and deletes data using the user's own Supabase client before calling `admin.deleteUser()`. The comment correctly notes this is belt-and-suspenders since `ON DELETE CASCADE` handles it. This is an acceptable defensive pattern and no change is required. Note: if a future table is added without `ON DELETE CASCADE` and not listed in the `tables` array, user data could persist after account deletion.

**Recommendation**: Consider adding a SQL comment or test documenting the cascade policy assumption, and update the array whenever new user-scoped tables are added.

---

#### CR-INFO-002 — Google OAuth state parameter is not cryptographically signed
**File**: `app/api/google/auth/route.ts` — Line 21
**Description**: The OAuth `state` parameter encodes `userId + encodedNext` in plain text. While the callback verifies `stateUserId === user.id` (which mitigates CSRF because an attacker cannot forge a session), a cryptographically signed state (HMAC) would prevent state tampering and would be the OAuth 2.0 best-practice recommendation (RFC 6749 §10.12). The current implementation is functionally safe for the threat model but would not pass a strict OAuth security audit.

**Recommendation**: Consider signing the state with HMAC-SHA256 using a server-side secret for stricter compliance. This is a low-priority hardening item.

## Positive Highlights

The following patterns demonstrate strong engineering practices worth preserving:

1. **Consistent Server Action boundary**: All mutations go through `'use server'` functions with `authedClient()` + Zod parsing before any DB call. This is applied uniformly across `tasks.ts`, `processing.ts`, `projects.ts`, `clarity.ts`, `logbook.ts`, and `attachments.ts`.

2. **RLS hardening migration**: `004_rls_hardening.sql` replaces broad `FOR ALL` policies with explicit per-operation policies and `REVOKE ALL ON user_integrations FROM anon`. This is security-by-design at the database layer.

3. **Manual transaction rollback in `clarity.ts`**: The two-step insert (task → clarity_session) includes a rollback on step 2 failure — correctly cleaning up orphaned tasks since Supabase JS client v2 doesn't support true BEGIN/COMMIT transactions. The same pattern is present in `projects.ts`.

4. **Google OAuth CSRF mitigation**: The callback at `/api/google/callback` validates `stateUserId === user.id` before accepting the authorization code, correctly defending against CSRF via the state parameter.

5. **File path ownership check in `deleteAttachment`**: `filePath.startsWith(${user.id}/)` prevents users from deleting other users' files by path manipulation, even though storage RLS also applies.

6. **Accessibility**: `ProcessingOverlay` correctly implements `role="dialog"`, `aria-modal="true"`, `aria-labelledby`, focus trap (`useFocusTrap`), focus management on step change, and keyboard navigation (Escape, Backspace, Alt+Arrow).

7. **Optimistic UI in `InboxList`**: Uses React 19's `useOptimistic` for instant feedback on delete, with undo support via toast — this is the correct pattern for perceived performance in task management UIs.

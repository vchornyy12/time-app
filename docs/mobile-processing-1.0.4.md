# Android 1.0.4 — повний сценарій обробки Inbox

23 жовтня 2026. versionCode 5. Виправляє обмеження 1.0.3, де Inbox можна
було лише перемістити в Next Actions.

## Поведінка

Натискання задачі Inbox відкриває GTD-майстер з тими самими питаннями й
результатами, що `components/tasks/ProcessingOverlay.tsx`:

1. Actionable? Ні → Trash / Notes.
2. До двох хвилин? Так → зробити зараз і Done.
3. Моє завдання? Ні → Waiting For: адресат, необов’язковий термін, контексти.
4. Конкретна дата/час? Так → Calendar: локальні дата/час, повторення.
   Відкласти → Someday / Maybe з необов’язковою датою перегляду.
5. Один крок? Так → конкретна Next Action, контексти, повторення.
   Ні → проєкт із назвою, критеріями результату, rough plan і першою дією.

Збереження виконується лише в кінцевій гілці. Back зберігає чернетки полів
у відкритому майстрі. Закриття після переходів вимагає підтвердження, а
Android Back повертає на попереднє питання. Повторне відправлення під час
запиту заблоковане. Редактор назви й контекстів доступний окремо.

Нова вкладка Lists дозволяє переглянути Waiting For, Calendar для всіх дат,
Someday / Maybe, Notes, Trash, Done та проєкти. Показує дати, адресата,
результат проєкту й план; можна відкрити першу дію та відновити задачу з
Trash в Inbox. Це базовий доступ до результатів обробки, а не повний CRUD
усіх розділів вебверсії.

## Спільна серверна поведінка

`POST /api/mobile/process-inbox` перевіряє Supabase bearer token сервером,
використовує user_id перевіреного користувача та його RLS-клієнт. Не покладається
на web cookies, user_id з тіла запиту або адміністративний доступ до задач.

Через request-local AsyncLocalStorage endpoint викликає існуючі вебдії:
`lib/actions/processing.ts`, `lib/actions/projects.ts`. Вкладені календарні
дії отримують той самий перевірений контекст. Тому календарна гілка запускає
ту саму Google Calendar синхронізацію, а делегування — ті самі follow-up
reminders; refresh tokens залишаються на сервері. Помилки Google залишаються
non-fatal, як у вебверсії. Нового OAuth-підключення на телефоні цей реліз
не додає; використовується наявна прив’язка акаунта.

Middleware пропускає cookie-перевірку лише для точного шляху цього endpoint;
сам endpoint вимагає bearer token й повертає JSON 401/404/409, а не редирект
на HTML-логін. Звичайні вебдії продовжують використовувати cookie-сесію.
Контекст не глобальний і не переноситься між запитами.

Звичайні processing updates перевіряють, що задача ще inbox; у мобільному
контексті також перевіряють початковий updated_at без втрати мікросекунд.
Нуль змінених рядків є помилкою. Проєкт створюється існуючим атомарним
`create_project_from_inbox`; повтори не створюють другий проєкт. Попередньо
оброблені задачі відхиляються HTTP-адаптером з 409. Нових SQL-міграцій немає.

Спільний discriminated union `lib/validation/inbox-command.ts` перевіряє
вхідні параметри на телефоні й сервері, включно з реальною календарною датою
для термінів/review date. Android використовує нативні date/time pickers.

## Перевірки

- 447 веб/серверних тестів у 34 файлах; 77 мобільних тестів у 9 файлах.
- Обидва TypeScript-проєкти, production Next.js build, Gradle release build,
  статичні перевірки APK та git diff --check.
- Production API: всі 8 кінцевих гілок на ізольованому тимчасовому акаунті;
  перевірено статуси й поля в базі, recurrence, проєкт із rough plan та
  first_step_task_id, відхилення повторних команд 409 і запиту без токена 401.
- API unit tests: перевірений власник, прихована RLS задача, невалідні дані,
  застаріла версія, dispatch до існуючих actions та скидання auth context.
- Нативні тести майстра проходять усі питання й кінцеві гілки, повернення,
  проектні поля, контексти, recurrence, помилку запиту й повторні натискання.
- Точний APK встановлюється поверх 1.0.3 на ARM64 Android 16 API 36.
- На цьому APK через інтерфейс пройдено всі 8 кінцевих гілок; нативні
  date/time pickers, дати перегляду, recurrence, адресата, критерії проєкту,
  rough plan і first_step_task_id підтверджено в базі. У Lists перевірено
  делеговану задачу та створений проєкт. Crash log після сценаріїв порожній.
- Фізичний OnePlus Nord 5 не тестувався. Google-акаунт не підключали до
  тимчасового користувача; створення реальних Google-подій окремо не
  перевірялося. Для цих дій використано той самий існуючий код, що у вебі.

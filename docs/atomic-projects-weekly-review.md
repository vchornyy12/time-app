# Проєкти та Weekly Review: другий пакет

## Що змінилося

Шість server actions проєктів викликають транзакційні PostgreSQL RPC. Вони працюють із правами користувача (`SECURITY INVOKER`), зберігають RLS і додатково перевіряють власника. Створення проєкту з Inbox, активація кроку та завершення кроку більше не складаються з окремих клієнтських записів із частковим rollback.

RPC блокують рядок проєкту перед редагуванням JSON-плану. Reorder працює з поточним планом: зберігає щойно додані кроки й не повертає вже активовані. Для активації UUID plan item стає ID задачі, тому повторний запит повертає попередній результат. Додавання кроку також приймає стабільний request ID. Створення проєкту повторно використовує origin task, якщо конвертація вже відбулася.

Карточки, деталі та review визначають активні зобов'язання за фактичними задачами. Старий pointer на Trash/Done/Inbox не вважається наступною дією. Waiting For і Calendar відображаються як окремі стани; завершувати їх пропонується через відповідний список, зі збереженням наявного календарного сценарію. Проєкт із незавершеними активними задачами або непорожнім планом не можна завершити через RPC.

Weekly Review спочатку збирає думки, потім пропонує розібрати Inbox. Count перечитується при поверненні до вкладки; непорожній Inbox можна залишити лише з явною позначкою про залишки. Крок огляду зберігається у localStorage з ключем конкретного користувача, Mind Sweep і його request IDs — у sessionStorage. Після часткового capture підтверджені рядки прибираються, решта зберігає ID для безпечного повтору. Збереження завершеного огляду виконується явною кнопкою, при помилці progress не очищується.

У списках Waiting For, Next Actions і Someday рядки прибираються після підтвердження запису. Збій читання не виглядає як порожній список, помилки змін показують retry/refresh. У Someday виправлено Clear date: він передає `null`, а не попередню дату зі state. Зміни через overlay перечитуються при його закритті.

## Порядок застосування

1. Звірити застосовані попередні міграції, зокрема `005_completed_at.sql`, колонку recurrence_rule та recurrence trigger. Не запускати всі старі SQL-файли повторно: не всі старі міграції ідемпотентні.
2. На тестовій базі застосувати [20261015000000_atomic_projects.sql](../supabase/migrations/20261015000000_atomic_projects.sql). Вона створює/оновлює функції та їхні дозволи; не переписує користувацькі дані. Повторне застосування перевірено локально.
3. Перевірити під входом: створення проєкту, порожні критерії завершення, активацію/повтор активації, add/reorder з двох вкладок, повторювану задачу, stale pointer, відмову в доступі іншому користувачу та повний review.
4. Застосувати цю міграцію на цільовій базі **перед деплоєм нового вебкоду**. Нові server actions залежать від шести RPC; небезпечного fallback на старі багатокрокові записи немає.
5. Викласти вебкод і повторити коротку перевірку під входом. Для відкату вебверсії нові RPC можна залишити в базі: вони сумісні зі старою схемою. Видаляти дані чи відкочувати старі міграції не потрібно.

Production-міграцію застосовано через SQL Editor Supabase; деталі перевірки наведені нижче. Вебкод ще не задеплоєно.

## Перевірки

- 404 Vitest-тести проходять, зокрема помилки capture/review, retry, відновлення прогресу, ізоляція browser progress за користувачем, реальний project health і невдалі зміни проєкту.
- TypeScript, production-збірка і цільовий ESLint змінених модулів проходять. Загальний lint репозиторію має відомі зауваження з першого аудиту.
- 12 SQL-сценаріїв проходять на PostgreSQL через PGlite: повторне застосування міграції, реальні RPC, RLS двох користувачів, anon grants, injected failures між записами й повний rollback, idempotency, stale reorder, recurrence та завершення проєкту.

Відтворення SQL-перевірок із кореня репозиторію без підключення до зовнішньої бази:

```sh
npm install --prefix /private/tmp/time24-db-tests --no-save --package-lock=false @electric-sql/pglite@0.5.10
node scripts/test-project-transactions.mjs /private/tmp/time24-db-tests/node_modules/@electric-sql/pglite/dist/index.js
```

PGlite виконує ці тести в одній локальній сесії. Вони перевіряють stale requests і транзакційний rollback, але не замінюють тест реальних одночасних транзакцій із двох PostgreSQL-з'єднань. Також локальний SQL harness не перевіряє production PostgREST schema cache або фактичну конфігурацію Supabase — це покриває перевірка на тестовому середовищі.

## Межі

- Progress огляду не синхронізується між пристроями. Mind Sweep відновлюється у поточній browser session; закриття сесії браузера може очистити sessionStorage. Якщо storage недоступний, огляд працює в пам'яті до reload.
- Нова міграція захищає операції цих RPC, а не довільні прямі записи у таблиці іншими клієнтами чи старими версіями коду.
- Фоновий outbox Google Calendar, pagination та production performance baseline залишаються окремими пунктами плану.

SQL-рішення звірено з [PostgreSQL row locking](https://www.postgresql.org/docs/current/explicit-locking.html) та [Supabase Database Functions](https://supabase.com/docs/guides/database/functions).


## Застосування в production

15.10.2026 за прямою вказівкою власника застосовано `20261015000000_atomic_projects.sql` у проєкті `fjbgxzayfcrpnxmwzkko`, гілка `main / PRODUCTION`, через авторизовану панель Supabase.

- Перед виконанням підтверджено потрібні колонки, recurrence trigger та RLS. Жодної з нових шести функцій раніше не було. Попередня зареєстрована міграція — `20260527114423:add_recurrence_rule`; інші передумови звірено з реальною схемою, а не лише з журналом.
- Виконано точний локальний SQL-файл (10969 байтів, SHA256 `bc6c962d294d7db5d16cb8af00a488b49716b387eb8de0c8e0f4bf96475d69fe`). Для запуску додано транзакційні таймаути `lock_timeout=5s`, `statement_timeout=60s`.
- У тій самій транзакції додано запис `20261015000000:atomic_projects` у `supabase_migrations.schema_migrations` та виконано `NOTIFY pgrst, 'reload schema'`. Поле `statements` у записі історії залишене NULL; джерело міграції зберігається у локальному SQL-файлі, а його checksum наведений тут.
- SQL Editor підтвердив `atomic_projects applied`; окремий наступний запит підтвердив запис історії.
- Перевірено MD5 тіла кожної з шести production-функцій: усі збігаються з локальним SQL. Для кожної підтверджено `SECURITY INVOKER`, EXECUTE для `authenticated` та відсутність EXECUTE для `anon`.
- RLS на `tasks` і `projects` залишився увімкненим. До та після: 240 tasks, 10 projects. Міграція не виконувала записів у ці таблиці.
- Вебкод ще не викладений. Авторизовані бізнес-сценарії через нову вебверсію в production поки не перевірялися.

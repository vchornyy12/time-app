# Аудит time24: швидкодія, надійність і GTD

Дата: 15.10.2026. Контекст: продакшин, 20 зареєстрованих користувачів за інформацією власника.

## Висновок

Поточна архітектура Next.js + Supabase має сенс для цього етапу. Код містить конкретні можливості скоротити очікування без переписування застосунку. Почати варто з вимірювання авторизованих сценаріїв, скорочення послідовних мережевих операцій і надійності capture. Кількість реєстрацій сама по собі не показує навантаження; ознак, які обґрунтовують більший сервер, в аудиті немає.

Для продукту головний напрям — довіра до системи: думка не губиться, наступна дія відповідає реальному стану проєкту, щотижневий огляд актуалізує всі зобов'язання. Нові великі функції поки мають нижчий пріоритет.

## Межі перевірки та факти

- Переглянуто вебмаршрути, server actions, основні компоненти задач/проєктів/огляду, SQL-міграції, конфігурацію Netlify і перевірок. Мобільний застосунок не проходив повного аудиту.
- `npm run test:run`: 16 файлів, 367 тестів проходять. Є попередження React `act` і розмірів Recharts у тестовому середовищі.
- `npx --no-install tsc --noEmit --incremental false`: проходить.
- `npm run lint`: 40 помилок, 32 попередження. Перевірка захоплює `mobile/eas-inspect-output*` із копіями коду; також є помилки у вихідному вебкоді, наприклад `WelcomeModal` та `InboxList`. Це стан інструментів якості, а не доказ причини затримок.
- Адресу `https://time24.pro` знайдено в metadata репозиторію. Публічний HEAD повернув 200 через Netlify, `cache-control: private,no-cache,no-store,...`, CDN miss/bypass.
- Одноразові GET без cookies: `/` — 200, TTFB 1,145 с, загалом 1,211 с; `/login` — 200, TTFB 0,059 с; `/inbox` — 307, TTFB 0,047 с. Другий і третій запити повторно використовували з'єднання. Це одиничні спостереження з машини аудиту, не p95 і не порівняльний бенчмарк. `/inbox` вимірює лише редирект без входу.
- Немає авторизованих production traces, EXPLAIN, метрик CPU/DB, перевірки фактично застосованих міграцій чи підтвердження, що продакшин відповідає цьому checkout. Нижче чітко розділено факти коду й гіпотези щодо їхнього впливу.
- Бізнес-логіку та продакшин-дані під час аудиту не змінено; створено лише цей план.

## Надійність, яка напряму впливає на GTD

### P1: Capture не повинен губити думки

`components/layout/QuickCaptureBar.tsx:120` очищає введення й файли до завершення збереження. Помилка показує загальний toast, але не відновлює текст. Помилки окремих upload пропускаються (`:140`) без повідомлення; файли завантажуються послідовно.

План: тримати окремі pending captures із текстом та станом; при помилці залишати доступними retry/edit. Не перезаписувати нове введення старою невдалою задачею. Для вкладень показувати результат кожного файлу та обмежений паралелізм. Додати request ID/idempotency для безпечного повтору. Постійне offline-збереження — окреме рішення після перевірки потреби; спочатку достатньо надійного відновлення в поточній сесії.

Приймання: штучно зламати insert та один upload; текст залишається доступним, retry не створює дубль, невдалий файл видно.

### P1: Проєктні зміни мають бути атомарними

`lib/actions/projects.ts:createProject` містить три окремі записи з частковим rollback. Помилка зв'язування залишає частково збережений стан. `promoteRoughPlanItem` окремо вставляє задачу та змінює JSON-план; error другого запису не перевіряється. Паралельні редагування JSON можуть перезаписувати одне одного.

План: транзакційні RPC з перевіркою власника, зв'язку task/project, очікуваного стану та блокуванням або контролем версії. Для promote — захист від повторної обробки одного plan item. Перевіряти помилки всіх записів. Оптимістичний UI повинен відкотитися й дозволити повтор при помилці.

Приймання: подвійний клік, паралельні вкладки та відмова посеред операції не залишають дубль задачі або напівстворений проєкт.

### P1: «Є наступна дія» має означати актуальну дію

`components/review/ReviewStep3Projects.tsx:65` використовує лише `first_step_task_id !== null`. Переміщення пов'язаної задачі в trash/inbox не завжди очищає посилання. У результаті огляд може показати «Next action set» для недоступної до виконання задачі. І навпаки, інша активна задача проєкту може існувати без цього pointer.

План: визначити стан проєкту за фактичними задачами — доступна next action, очікування делегованої відповіді, календарне зобов'язання або справді немає наступного кроку. Pointer може бути зручним виділенням, але не єдиним джерелом істини. Після завершення кроку запропонувати вибрати наступний або завершити проєкт; не обов'язково автоматично активувати залежні кроки.

## Рекомендації щодо продукту й GTD

1. **Виправити Weekly Review.** У `WeeklyReviewFlow` спочатку Get Clear, потім Mind Sweep; нові записи після Mind Sweep не проходять окремого processing-кроку. Збирати вхідне → mind sweep → розбирати Inbox → переглядати календар минулого/майбутнього, Waiting For, Projects, Next Actions, Someday → завершувати огляд явною дією. Зараз календар лише згадується текстом. Додати збереження прогресу й повернення; `step` нині живе тільки в `useState`. Дозволити усвідомлений пропуск із видимими залишками, не заявляти автоматично, що все очищено. У summary `saveWeeklyReviewComplete` запускається при монтуванні, а його помилка приховується — потрібні підтвердження і retry.
2. **Полегшити рішення «що робити зараз».** Контексти вже є. Наступний невеликий експеримент — необов'язкові оцінки часу та енергії з фільтрами; не додавати обов'язкові поля до швидкого capture. Показувати реальні часові зобов'язання поруч із доступними діями. Корисність перевірити на користувачах до розширення моделі.
3. **Розділити значення дат.** `due_date` зараз використовується і для дедлайну, і follow-up, і дати перегляду Someday. На переходах між статусами старе значення може зберігатися (`moveToNextActions`, `processToSomedayMaybe`). Визначити окрему семантику deadline/review/follow-up і правила очищення або перенесення; міграція має зберегти існуючі наміри користувача. Календар залишати для конкретних часових зобов'язань.
4. **Спростити старт для нового користувача.** Запропонувати короткий шлях: записати кілька думок → розібрати одну → визначити наступну дію → обрати час огляду. У навігації зараз 13 розділів; другорядні Analytics, Success Diary і Clarity Protocol можна зробити менш помітними. Перевірити це короткими сесіями, не міняти навігацію лише на підставі цього огляду коду.
5. **Змістити акцент аналітики на стан системи.** Поряд із завершеними задачами показувати старі записи Inbox, проєкти без актуального кроку, follow-up, що потребують уваги, і регулярність review. Кількість завершень сама по собі погано відображає якість GTD.
6. **Прибрати вигадані резервні лічильники.** `lib/stats.ts:6` при відмові RPC підставляє 120 користувачів і 4800 задач. Фактичні лічильники в проді не перевірялися. Краще приховати секцію або показувати останній достовірний результат із зрозумілим станом, ніж вигадане число.
7. **Виправити пошук як шлях до конкретної задачі.** `SearchPalette` веде на загальний список, не відкриває знайдену задачу; done за замовчуванням веде на Inbox. Передавати ID і відкривати картку, мати маршрут для done. Додати захист від запізнілої відповіді попереднього пошуку та видимий error state.

Офіційний [GTD Weekly Review](https://gettingthingsdone.com/2009/05/the-gtd-weekly-review/) включає актуалізацію календаря, списків і проєктів. Пропозиції щодо UI, часу/енергії та онбордингу тут є продуктовими гіпотезами, які слід перевірити на цій аудиторії.

## План виконання

Оцінки — орієнтовні робочі дні одного розробника, після підтвердження production-конфігурації; це не обіцянка строку чи прискорення.

| Етап | Робота | Орієнтир | Умова завершення |
| --- | --- | --- | --- |
| 0. Базові виміри | Авторизований тестовий акаунт; trace Inbox, Next Actions, capture, complete, processing, project detail. Окремо cold/warm, desktop/mobile, Google on/off. Звірити commit, регіони Netlify/Supabase, застосовані міграції та DB errors. | 0,5–1 день | Таблиця p50/p95, запитів і payload до змін; відомо, де саме витрачається час. |
| 1. Швидкі зміни | Паралельний layout, спільний auth helper, усунення зайвих cleanup-запитів, локальні context-фільтри, цільова revalidation. Паралельно відновлення невдалого capture. | 2–4 дні | Повторні виміри тих самих сценаріїв; немає застарілого sidebar/списків і втрати введення. |
| 2. Довіра до стану | Транзакції create/promote, актуальний project health, помилки та rollback; виправлення порядку review, його завершення та resume. | 3–5 днів | Збої й повторні дії не руйнують стан; review повертається до зібраного вхідного та зберігається достовірно. |
| 3. Умовні оптимізації | За traces: outbox Google, payload/pagination, EXPLAIN та потрібні індекси/RLS, landing/JS. | 2–5 днів залежно від знахідок | Прибрано виміряний bottleneck; для Google є retry та видимий статус. |
| 4. Продуктовий цикл | 3–5 коротких розмов/спостережень; спрощений старт або фільтри часу/енергії як один експеримент. | 1 тиждень спостереження | Є конкретне підтвердження покращення сценарію й повернення користувачів. |

Безпечний rollout: малі окремі зміни, staging і тестовий акаунт; backward-compatible міграції; перевірка web/mobile контрактів; для кожної зміни визначений спосіб відкату. Не виконувати destructive rollback міграцій з користувацькими даними.

## Як вимірювати результат

- Розділити час видимого відгуку, час надійного запису та час зовнішньої синхронізації. Оптимістична анімація не є підтвердженням збереження.
- Додати серверні таймінги auth/DB/Google/RSC, request correlation та збір помилок. Не логувати назви задач, тексти нотаток, файли чи токени.
- Для повторюваного бенчмарку використати, наприклад, 20 вимірів кожного сценарію з фіксованим набором тестових даних, окремо 50/500/2000 задач. Це тестові обсяги, не твердження про поточні дані. Для production p95 на малій аудиторії потрібен довший період і кількість спостережень поруч із метрикою.
- Початкові цілі для узгодженого регіону/пристрою: видимий відгук до 100 мс, warm-перехід до придатного списку p95 до 800 мс, локальний запис capture/complete p95 до 700 мс, INP до 200 мс, LCP до 2,5 с. Це цілі, не результати аудиту; уточнити після baseline.
- Воронка: реєстрація → перший capture → перший processing → перша next action → review → повернення через тиждень. Аналізувати абсолютні числа разом із частками; для 20 реєстрацій великі A/B-тести не є першочерговим інструментом.

## Технічні джерела

- [Next.js: request memoization / React cache](https://nextjs.org/docs/app/guides/caching-without-cache-components) — дедуплікація в межах render, без спільного кешування приватних даних між користувачами.
- [Next.js: revalidatePath](https://nextjs.org/docs/app/api-reference/functions/revalidatePath) — область інвалідації та оновлення UI через server actions.
- [Supabase: RLS performance](https://supabase.com/docs/guides/database/postgres/row-level-security) — індекси, явні фільтри, `(select auth.uid())` та обмеження ролей.

Наступна конкретна робота: зняти baseline під входом і виконати етап 1, потім повторно порівняти ті самі сценарії.

## Реалізація: перший пакет виправлень

Локально підготовлено 15.10.2026:

- Спільні Supabase client і перевірка користувача через request-scoped React `cache`; вебсторінки та `authedClient` використовують спільний результат. Middleware зберігає власну перевірку.
- Незалежні запити sidebar виконуються паралельно, з незалежним fallback при відмові.
- Reminder cleanup повторно використовує вже перевірений auth-контекст дії. Внутрішній helper позначено `server-only`; зовнішня server action перевіряє користувача як раніше.
- Контекст Next Actions береться з URL і змінюється через native History API, без серверної навігації. Параметри та hash зберігаються. Додаткова передача `initialContext` із сервера більше не потрібна.
- З capture та завершення Next Action прибрано додатковий `router.refresh`; server actions зберігають revalidation для оновлення даних.
- Capture зберігає pending/failed записи окремо від нового введення. Retry використовує той самий UUID; duplicate insert ігнорується, а перед підтвердженням повтору перевіряється власник. Повтор не перезаписує вже збережену задачу.
- Вкладення завантажуються максимум по три паралельно, зі стабільними шляхами та видимим retry при помилці upload або metadata. Повторний upload розпізнає відповіді «вже існує», не потребуючи нових UPDATE-політик storage.
- Додано 12 regression-тестів: відмова capture, нове введення під час запиту, idempotency/ownership, часткові uploads із різними форматами duplicate error, відмова metadata та URL-фільтри.

Перевірки: 379 тестів у 19 файлах проходять; TypeScript проходить; production build проходить. Цільовий ESLint зміненого коду не має помилок; у `projects/[id]/page.tsx` лишається попереднє попередження невикористаної змінної. Загальний lint репозиторію не виправлявся цим пакетом.

Обмеження: черга capture живе в поточній вкладці, не є offline-сховищем і не відновлюється після reload. Фоновий Google outbox, транзакційні RPC, перегляд GTD review та решта пунктів аудиту залишаються наступними пакетами. Немає авторизованого production baseline або E2E з реальним Supabase; відсоток прискорення не виміряно. Деплой і міграції не виконувалися.

Деталі API звірено з [Next.js Native History API](https://nextjs.org/docs/app/getting-started/linking-and-navigating) та [Supabase Standard Uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads).

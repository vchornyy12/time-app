# Відповідність Android вебверсії time24

Дата: 23 жовтня 2026. Базова мобільна версія: 1.0.2, versionCode 3.
Статус: аудит коду завершено; у 1.0.3 реалізовано перший блок етапу 1,
у 1.0.4 — усі гілки Inbox Processing та базовий доступ до списків призначення.
Решта пунктів нижче залишається планом.

### Прогрес: Android 1.0.4

Inbox відкриває той самий GTD-сценарій, що у вебі: Trash, Notes, Done,
Waiting For, Calendar, Someday/Maybe, Next Action або проєкт. Є необов’язкові
терміни/дати перегляду, нативний вибір часу й recurrence, rough plan і перший
крок. Мобільний HTTP endpoint використовує перевірену сесію та існуючі
вебдії, разом із Google-побічними діями. Нових міграцій немає.

Вкладка Lists надає базовий перегляд результатів, деталей проєкту й першої
дії, відновлення з Trash. Повне керування цими розділами ще залишається
в плані. [Перевірки й межі релізу](mobile-processing-1.0.4.md).

### Прогрес: Android 1.0.3

Реалізовано деталі задач із Today/Inbox/Next Actions, редагування назви й
контекстів, перехід Inbox → Next Action → Done, окремий список Next Actions
із серверною фільтрацією контекстів, парольний вхід для наявних акаунтів.
Вхід через magic link збережено. Є перевірка версії задачі перед збереженням,
підтвердження втрати незбережених правок і захист від подвійного натискання.

Валідація використовує спільні схеми вебверсії; завершення next action
проєкту викликає наявний атомарний RPC. Нових міграцій не потрібно.
Звичайні правки задач поки працюють через користувацький Supabase/RLS;
загальний HTTP-контракт серверних команд, інші гілки обробки, Notes/Trash
та керування збереженим списком контекстів ще не реалізовані.

Перевірено 64 мобільними тестами, 89 тестами спільних схем, TypeScript,
release-збіркою та наскрізним запуском APK на ARM64 Android 16.
Деталі: [звіт збірки 1.0.3](mobile-parity-1.0.3.md).

## Висновок

Повна функціональна відповідність можлива без заміни React Native застосунку.
Android був спроєктований як companion: швидке збереження думок, перегляд
Inbox і сьогоднішніх задач. Це підтверджує початкова
[специфікація](superpowers/specs/2026-04-20-mobile-app-design.md).
Тому різниця з вебверсією суттєва, а не зводиться до кількох відсутніх екранів.

Основний пріоритет — замкнути GTD-цикл на телефоні: записати → обробити →
організувати → виконати → переглянути систему. Зараз обробка Inbox і проєкти
вимагають вебверсії. Перенесення лише списків цього не вирішить.

Це аудит локального коду, а не перевірка всіх сценаріїв на продакшені.
Наявність міграції у репозиторії не підтверджує її застосування в базі.
У межах аудиту продакшн, дані користувачів і встановлений APK не змінювалися.

## Виявлені технічні залежності

### Спільна база не забезпечує однакову поведінку автоматично

Мобільний код напряму читає й змінює Supabase. Вебверсія виконує частину
операцій у Next.js Server Actions, включно з побічними діями Google Calendar.
Їх не можна імпортувати в React Native. Читання даних спільне, але однаковий
результат складних операцій треба забезпечити окремо.

Мобільне завершення задачі зараз складається з двох запитів: завершення
задачі та очищення first_step_task_id проєкту. Частковий збій може завершити
задачу, але показати користувачу помилку. Проєктні сценарії треба перевести
на наявні атомарні RPC там, де вони відповідають операції, і визначити
безпечний повтор решти команд. Не слід копіювати цю послідовність у нові екрани.

Поточні списки оновлюються при фокусі, поверненні застосунку на передній план
та pull-to-refresh. Realtime-підписок і повноцінного offline-режиму немає.
Спільна база означає спільні збережені дані, але не миттєве оновлення відкритого екрана.

### Серверні можливості

У `app/api` зараз є Google auth/callback; універсального мобільного API для
доменних операцій немає. Google OAuth використовує вебсесію через cookies,
тому просте відкриття цього URL не авторизує користувача з мобільною сесією.
Підключення календаря й Google-вхід — окремі сценарії, обидва треба перевірити.

Рекомендована реалізація:

- Винести доменні операції з Server Actions у серверні сервіси без залежності
  від `revalidatePath` і редиректів. Server Actions залишити вебобгортками.
- Для Android додати версіоновані HTTP-команди до тих самих сервісів.
  Перевіряти Supabase access token на сервері; user_id брати з перевіреної
  сесії. Для звичайних операцій з даними зберегти користувацький контекст і RLS.
- Для простого читання списків можна залишити мобільний Supabase-клієнт:
  вибір потрібних колонок, пагінація, фільтри на сервері.
- Привілейовані дії, Google refresh tokens, service-role key та очищення
  облікового запису залишити на сервері. Не передавати веб cookies або
  токени через URL. Перед реалізацією OAuth визначити окремий безпечний
  сценарій прив’язки мобільної сесії та повернення в застосунок.
- Команди з зовнішніми побічними діями мають визначений результат повтору,
  окремий стан помилки синхронізації і можливість retry без дублювання подій.

Це не вимагає окремого бекенд-проєкту: поточний Next.js може обслуговувати
обидва клієнти. Supabase RPC залишаються спільним місцем атомарних змін.

### Спільний код

`@shared` у mobile зараз веде на `../lib`. Типи вже використовуються спільно.
Але `lib/validation/schemas.ts` імпортує `@/lib/types`, а мобільна конфігурація
визначає лише `@shared`. Перед реальним перевикористанням схем треба прибрати
вебспецифічний alias з їхніх внутрішніх імпортів і явно забезпечити мобільну
залежність Zod. Наявність alias сама по собі не робить усю папку lib спільною.

Спільними мають бути типи, валідація, дозволені переходи й розрахунки.
Навігація, сховище сесії та UI залишаються платформними. Web React і mobile
React не потрібно вирівнювати: у mobile версія має відповідати native renderer.

Повторення задач уже описане SQL-тригером у репозиторії. Не генерувати наступний
екземпляр додатково в Android; перевірити фактичну серверну поведінку на тестових
даних. Аудит не підтверджував поточний стан цього тригера в production.

## План реалізації та критерії приймання

### Етап 1. Основа та перший наскрізний GTD-сценарій

- [ ] Сформувати спільні доменні схеми й серверний контракт для змін задач.
- [ ] Додати навігацію Today / Inbox / Next Actions / Projects / More;
  Projects і решту розділів показувати доступними після їх реалізації.
- [x] Додати деталі задачі, редагування назви й вибір контекстів.
- [x] Реалізувати перший завершений сценарій Inbox → Next Action → Done.
- [x] Додати базові виходи обробки до Notes і Trash та доступ до результату.
- [x] Додати парольний вхід для наявних користувачів вебверсії.

Приймання: створити задачу на телефоні, обробити її як next action з
контекстами, відредагувати й завершити; перевірити ті самі дані у вебверсії.
Протилежний напрямок — створення у вебі й робота в Android — також працює.
При повторному натисканні або таймауті немає дубля задачі; чужі дані недоступні.

### Етап 2. Повсякденні списки та решта обробки

- [ ] Waiting For, Someday / Maybe, Notes, Trash з усіма діями матриці.
- [ ] Calendar для інших дат, прострочених задач і перенесення часу.
- [ ] Відповідні гілки Processing: делегування, планування, review date,
  двохвилинне завершення, recurrence; гілка проєкту завершується на етапі 3.
- [ ] Фільтри й керування контекстами; поля делегування й термінів.
- [ ] Єдиний контракт календарних змін включає Google-побічні дії для вже
  підключених користувачів; до реалізації синхронізації відповідний сценарій
  не позначати завершеним. Налаштування підключення — етап 5.

Приймання: кожна гілка обробки приводить до очікуваного списку, дані можна
змінити, повернути в Inbox або відновити з кошика. Перевірити часові пояси,
перехід через північ, повторення і retry синхронізації. Остаточне видалення
перевіряти лише на тестових записах із явним підтвердженням у UI.

### Етап 3. Проєкти й пошук

- [ ] Створення проєкту з Inbox: назва, результат, rough plan, перший крок.
- [ ] Списки й деталі проєктів, health-індикатори, усі наявні операції плану.
- [ ] Атомарні RPC створення/завершення/просування/перестановки кроків.
- [ ] Пошук задач і проєктів, перехід із результату до правильних деталей.

Приймання: повний цикл проєкту з телефона, правильний first step після
кожної операції, одночасні дії з веба й Android не гублять кроки й не
створюють дублікати; активні та завершені проєкти відображаються однаково.

### Етап 4. Огляд і допоміжні робочі сценарії

- [ ] Weekly Review: Mind Sweep → Inbox → Waiting For → Projects →
  Next Actions → Someday / Maybe → Summary.
- [ ] Локальне відновлення кроку огляду окремо для кожного акаунта;
  спільна дата завершеного огляду через user_preferences.
- [ ] Success Diary з рефлексіями, Clarity Protocol, Analytics.

Приймання: огляд можна перервати й продовжити, дії з попередніх етапів
доступні всередині нього, завершення фіксує дату. Diary правильно групує
локальні дні; рефлексія, Clarity-задача та показники збігаються між клієнтами.
Синхронізація незавершеного кроку між пристроями — окрема можливість,
її немає у поточному вебконтракті.

### Етап 5. Інтеграції, налаштування та остаточна відповідність

- [ ] Google-вхід, реєстрація, password reset і безпечні deep links.
- [ ] Google Calendar connect/disconnect та весь цикл подій і reminders.
- [ ] Вкладення з наявними обмеженнями: до 20 файлів, до 10 MiB на файл.
- [ ] Налаштування облікового запису та серверне видалення з тим самим
  правилом недавнього входу, що у вебверсії.

Приймання: повний прогін матриці. Для OAuth перевірити успіх, відмову,
прострочене повернення й неправильну сесію. Файли доступні лише власнику,
від’єднання Google та видалення тестового акаунта очищають належні ресурси.

## Перевірки перед кожним APK

1. Доменні тести й TypeScript для змінених сценаріїв; обов’язкова перевірка
   точного збігу React із native renderer.
2. Release build, статична перевірка APK, незмінний підпис і збільшений versionCode.
3. Встановлення поверх попереднього APK, холодний запуск, повторний запуск,
   повернення з background і журнал падінь на Android-емуляторі.
4. Наскрізний сценарій нових можливостей із виділеними тестовими акаунтами:
   Android → web і web → Android, з явним оновленням списків.
5. Погана мережа, повтор натискання, logout/login іншим користувачем,
   пагінація понад 50 записів та порожні стани.
6. Пряме посилання на APK із перевіреним checksum. OnePlus Nord 5 —
   окрема фізична перевірка користувачем, без вимоги USB.

Поточна контрольна точка аудиту: 42 мобільні тести у 6 файлах проходять;
TypeScript для mobile проходить. Це не підтверджує майбутні функції матриці.

## Що не входить у відповідність вебверсії

Повний offline CRUD, push-нагадування, віджет Android, системний Share target,
біометричне блокування й iOS можуть покращити мобільний досвід, але це окремі
можливості. Вони не повинні затримувати замикання GTD-циклу. Не потрібен
одночасний редизайн або перенесення всього проєкту в новий стек.
